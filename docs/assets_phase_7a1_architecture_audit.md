# Finote v1.3.0 — Phase 7A.1 Architecture Audit

Status: **READY for Phase 7A.2**

Scope: inspection and planning only. This audit does not create tables, change
the Drift schema, add UI, or add networking.

## 1. Current Architecture

### Drift schema

- Current `schemaVersion` is **8** in `lib/core/database/app_database.dart`.
- Tables are `accounts`, `categories`, `transactions`, `transfers`, and
  `settings`.
- Integer SQLite primary keys are local identities. Entities that survive
  migration also have unique UUIDs generated by Drift client defaults.
- Financial transaction dates are date-only text in `YYYY-MM-DD` format through
  `DateOnlyConverter`; metadata timestamps are UTC `DateTime` values.
- Important records use nullable `deleted_at` for soft deletion. Accounts use
  `is_active` for archive/reactivate semantics. Settings use `key` as the
  primary key and have no soft delete.
- Money is stored as SQLite `INTEGER`; transaction and transfer amounts must be
  positive. Account initial balance is also an integer and must be non-negative.
- Existing indexes cover transaction date/category/type/deleted state/account,
  legacy identity, receipt fingerprint, account activity, and transfer account,
  date, and deleted state.

### Migration history

The existing additive migrations are:

1. Create the original tables.
2. Add receipt fingerprint compatibility.
3. Create accounts and ensure the default account.
4. Add nullable transaction account relation, backfill it, and validate it.
5. Add transaction account index.
6. Create transfers.
7. Repair account and transfer indexes.

The next migration must be **v9**, implemented as one additive upgrade from
v8. It must not mutate existing transaction rows.

### Transactions, accounts, and transfers

- `Transactions` has local id, UUID, string-backed `TransactionType`, nullable
  account relation, required category relation, integer amount, title/note,
  date, string-backed source, legacy identity, receipt fingerprint, UTC
  timestamps, and nullable soft-delete timestamp.
- `TransactionRepository` validates category/type, resolves an active account,
  writes inside a database transaction where multiple checks are involved, and
  soft-deletes instead of physically deleting normal records.
- `Accounts` has local id, UUID, name, string-backed account type, integer
  initial balance, `is_active`, default marker, and UTC timestamps.
- `AccountRepository` derives balances from initial balance, active transactions,
  and active transfers. Accounts with history cannot be deleted through the
  normal safe-deletion path; archive/reactivate is the established behavior.
- `Transfers` has local id, UUID, restricted account foreign keys, integer
  amount, date, note, timestamps, soft delete, and a same-account check.
  Transfers are separate from income and expense.

### Reports and Dashboard

`ReportRepository` aggregates active transaction income/expense and transfer
summary from SQLite using `ReportFilter`. Transfer amounts are deliberately
kept out of income, expense, and net balance. Charts use the same report
repository and derive category, trend, and account views from the same records.

`DashboardRepository` derives monthly cashflow from active transactions and
Total Assets from account summaries. It does not currently know about
portfolio holdings. Asset value must therefore be integrated later through a
separate portfolio/net-worth calculation and must not be added to current
income/expense queries.

### Existing investment cashflow

The current category defaults contain `Investasi` as an income category. The
repository has no stable semantic category key and no code references to
`Pembelian Aset` or `Penjualan Aset`. User data may contain those names, but
display-name matching is not a safe long-term identifier.

Conclusion: no category migration or historical reconstruction is allowed.
Future investment-cashflow reporting needs a deliberate semantic-category
strategy, preferably a stable system key added in a separate scoped change.

## 2. Backup, Restore, and Legacy Compatibility

### Backup

`BackupService` creates a SQLite snapshot with `VACUUM INTO`, stores it as
`database.sqlite` inside a ZIP, and writes `manifest.json`. The manifest has
backup version `1`, application name, database version, creation timestamp, and
app version. Because backup is a raw SQLite snapshot, new asset tables are
included automatically once they exist.

### Restore

Restore validates ZIP contents, manifest, database version, SQLite integrity,
foreign-key integrity, required tables, required columns, required indexes, and
existing Finote invariants. Older databases are opened through `AppDatabase`
to run migrations before validation. A safety backup is created before the live
database is replaced, with rollback support if replacement fails.

When schema v9 exists, restore validation must be extended to require the asset
tables and their critical columns/indexes. No backup format version bump is
needed for raw SQLite schema additions, but the manifest database version will
move from 8 to 9.

### Legacy import

Legacy databases are opened read-only. Import maps legacy type `0`/`1` to
Finote expense/income, creates or reuses categories, assigns the default
account, stores legacy source/id, and runs atomically. It does not currently
know about assets.

Legacy import must remain unchanged for 7A.2. It must not create assets,
opening positions, asset activities, symbols, quantities, or prices from old
cashflow rows.

## 3. Recommended Asset Domain

### Asset model

Recommend a new `assets` table and `AssetRecord` with:

- `id`: auto-incrementing local integer primary key;
- `uuid`: unique client-generated UUID;
- `symbol`: user-facing symbol, nullable for custom assets if needed;
- `normalized_symbol`: canonical lookup value;
- `name`: required display name;
- `asset_type`: stable string value: `stock`, `crypto`, `mutualFund`, `gold`,
  or `other`;
- `pricing_mode`: stable string value: `api` or `manual`;
- `currency`: initial default `IDR`;
- `unit_label`: optional user-facing unit such as `share`, `gram`, or `unit`;
- `is_active`: archive/reactivate state, matching Accounts;
- `created_at` and `updated_at`: UTC metadata timestamps.

Do not add mutable current quantity, current value, cost basis, or current
price to `assets`. These are derived or separately persisted state.

`asset_type + normalized_symbol` should be the uniqueness boundary where a
symbol exists. A custom asset without a meaningful symbol should use a stable
generated identity rather than forcing a fake symbol. Display casing remains
the user's choice; normalization is only for matching and uniqueness.

### Asset activity model

Recommend a new `asset_transactions` table and `AssetTransactionRecord` with:

- `id`, `uuid`;
- `asset_id` with a restricted foreign key;
- `action`: stable string `openingPosition`, `buy`, `sell`, or `adjustment`;
- `quantity_scaled`: signed/int64 fixed-point quantity;
- `price_amount`: nullable integer unit price;
- `total_amount`: nullable integer monetary total;
- `transaction_date`: date-only text using the existing converter;
- nullable note;
- nullable `source_transaction_id` restricted to `transactions.id`;
- `created_at`, `updated_at`, and nullable `deleted_at`.

Only `adjustment` is signed by default. Opening, buy, and sell quantities are
stored positive; holdings logic applies `+` to opening/buy and `-` to sell.
This avoids an ambiguous sign convention. Adjustment accepts positive or
negative values and must be documented as a signed correction.

Recommended checks:

- quantity is non-zero;
- opening/buy/sell quantity is positive;
- price and total amount are nullable;
- no source transaction is required;
- unknown enum strings fail conversion rather than being reinterpreted.

### Opening Position

Opening Position should be an `asset_transactions` row with
`action = openingPosition`, not a second field on `assets`. This provides one
auditable activity stream and makes the future formula uniform:

```text
holdings = openingPosition + buy - sell + adjustment
```

An opening position may have quantity with both price and total amount null.
That is the valid `cost basis unknown` state.

### Cost basis

Unknown cost basis is not zero. Future aggregation must expose three separate
states:

- current value: available when a current price exists;
- historical cost basis: known only when sufficient activity data exists;
- historical P/L: unavailable when cost basis is incomplete.

`Net Cash Invested` must never be used as a substitute for cost basis or P/L.

## 4. Deterministic Quantity and Money Strategy

### Quantity recommendation

Use one fixed-point representation for all asset quantities:

```text
quantity_scaled = quantity × 100,000,000
```

Store the result as SQLite `INTEGER`/Dart `int`, with exact integer parsing
and formatting in a small domain value object. This supports the required
examples exactly:

- `0.015` → `1,500,000`;
- `0.000125` → `12,500`;
- `5.25` → `525,000,000`;
- `123.4567` → `12,345,670,000`.

The fixed scale avoids binary floating-point drift, requires no new decimal
dependency, and keeps future holdings aggregation efficient. Input must reject
more than eight fractional decimal places and int64 overflow. The value object
must never use `double` for canonical parsing or arithmetic.

This is a deliberate v1.3 ceiling: quantities needing more than eight decimal
places are unsupported until the representation is revisited.

### Stock quantity

Store **shares** as the canonical stock quantity, using the same fixed-point
container with whole-share values in normal use. One Indonesian lot is 100
shares, so `12 lot` is stored as `1200 shares`. Lot is presentation/input
convenience, not a second source of truth. Later UI may display both shares and
lots.

### Money and price

Keep financial amounts as integer IDR. `total_amount` and initial manual/API
prices should be integer IDR per unit. Do not add `double` columns. If a future
provider requires sub-IDR pricing, define a separate explicit scaled monetary
representation before implementation; do not silently mix precisions.

## 5. Activity and Cashflow Design

### Buy

Future buy flow should be one atomic operation:

1. validate active asset/account and positive quantity;
2. create or accept exactly one expense transaction in category semantics for
   asset purchase;
3. create one `buy` activity with the transaction id;
4. commit both or neither.

The activity relation is nullable so opening and historical/manual activities
remain valid without cashflow.

### Sell

Future sell flow should validate `sell quantity <= derived active holdings`,
create exactly one income transaction in the asset-sale category, create one
`sell` activity linked to it, and commit atomically. Short selling is not
supported.

### Duplicate cashflow prevention

The repository/service that owns the economic operation must create the pair,
not two independent UI calls. Before creating a linked cashflow, check that the
activity does not already reference a transaction and that the transaction is
not already linked to another asset activity. A unique nullable index on
`source_transaction_id` is recommended so one cashflow cannot back multiple
activities.

Existing `Pembelian Aset` and `Penjualan Aset` rows remain valid with a null
source relation. No historical backfill is performed.

### Adjustment

Adjustment changes derived holdings only. It does not create income, expense,
transfer, or account movement. Positive and negative signed adjustments must be
visible in the activity history and included in holdings calculations.

## 6. Prices, Portfolio, and Market API Plan

### Local price architecture

Do not add price columns to `assets` and do not create multiple current-price
sources. Recommend one future `asset_prices` table, introduced with Phase
7B.3/7B.4, containing one latest row per asset:

- `asset_id`;
- integer IDR `price`;
- currency;
- nullable market-updated timestamp;
- local-updated/fetched timestamp;
- source `manual` or `api`;
- optional stale metadata.

No historical prices, candles, OHLC, or time-series tables are needed. Manual
and API last-known prices should use this same architecture. Last-known API
prices are rebuildable cache and are not backup-critical; holdings and manual
price state are backup-critical once introduced.

### Market API

No HTTP/Dio/client abstraction exists in the current Flutter codebase. Current
network-related code is limited to opening a privacy-policy URL. Do not add a
network dependency in 7A.1 or 7A.2.

When implemented, use one `MarketRepository`/client boundary behind the
normalized Finote Market API. Flutter models should contain symbol, name,
asset type, integer price, currency, change, change percent, market status,
stale state, and updated timestamp. Provider-specific Yahoo/CoinGecko/Binance
formats must not reach the domain.

Use `POST /api/v1/market/quotes` for a batch request. Send only symbols, asset
types, and currency. Never send quantities, balances, accounts, notes,
transactions, portfolio value, or net worth.

Offline flow:

```text
load local activities and assets
derive holdings locally
load local manual/last-known prices
render immediately
refresh one batch asynchronously
persist normalized latest prices
```

Failure of the API must only affect fresh prices, never local holdings or core
finance.

### Aggregation and Net Worth

Future `PortfolioRepository`/aggregation service should calculate holdings from
active activity rows, ideally with one grouped SQL query or one query followed
by deterministic integer aggregation. It must not use `assets.current_quantity`.

```text
Portfolio Value = SUM(holding quantity × current unit price)
Net Worth = Cash / Wallet Assets + Portfolio Value
```

Transfers do not affect portfolio holdings. Market price changes do not affect
income, expense, or net cashflow.

Historical investment cashflow remains a separate report:

```text
Purchase total = active expense rows with stable purchase semantic key
Sale total     = active income rows with stable sale semantic key
Net Cash Invested = Purchase total - Sale total
```

The current category schema lacks those stable semantic keys; do not implement
this matching by display string in 7A.2.

## 7. Riverpod and Navigation Plan

Current providers are simple `Provider`, `StreamProvider`, `FutureProvider`,
and family providers built around repositories and the shared `databaseProvider`.
Follow that convention later with only the providers needed by each phase:

- `assetsProvider` for active/all asset records;
- `assetActivitiesProvider(assetId)` for activity history;
- one holdings aggregation provider when holdings are implemented;
- one portfolio aggregation provider when portfolio UI exists;
- market quote provider only when the API phase exists.

Do not create UI-specific duplicate repositories or providers.

The current shell has four `NavigationBar` destinations: Beranda, Transaksi,
Laporan, and Pengaturan. Portfolio is conceptually distinct from Reports and
should eventually be a primary navigation destination, likely a fifth
`Portofolio` destination, rather than being hidden inside Reports. This remains
a future navigation decision and is not implemented in 7A.1.

## 8. Migration and Backup Plan

Phase 7A.2 should increment schema version exactly once, from **8 to 9**, and
add only:

1. `assets`;
2. `asset_transactions`;
3. justified indexes for normalized asset identity, activity asset/date/delete
   state, and nullable source transaction identity.

No existing table or row needs mutation. Fresh installs use `createAll`; v8
databases run the additive creation path. Existing users must have zero asset
rows after upgrade unless a future explicit user action creates them.

Raw SQLite backups include the tables automatically. Restore validation must
be updated for v9 required tables/columns/indexes. Explicit asset backup
serialization is not needed because none exists today.

Recommended future restore ordering for serialized formats is assets, asset
activities, then price/manual state. Existing raw snapshot restore already
preserves SQLite foreign-key ordering through the file and migration checks.

## 9. Risks and Edge-Case Policies

| Case | Recommended policy |
| --- | --- |
| Sell greater than holding | Block normal sell; no short selling |
| Negative adjustment | Allow as signed correction, validate resulting holding at workflow boundary |
| Zero quantity | Reject activity; zero holding may exist as a derived result |
| Fractional quantity | Fixed-point 1e8 integer, exact parsing |
| Unknown cost basis | Null price/total; display P/L unavailable, never zero |
| No current price | Show holding, value unavailable |
| Stale price | Show last-known value with stale marker |
| Manual asset | Same asset/activity/quantity model, manual pricing mode |
| Unsupported/delisted symbol | Keep local asset and holdings; quote refresh reports unavailable |
| Archived asset | Keep history and derived records; exclude from active-entry choices |
| Duplicate symbol | Permit across asset types; unique type + normalized symbol where present |
| Currency mismatch | Reject or explicitly handle before valuation; no implicit FX |
| API unavailable | Keep portfolio/local finance usable |
| Transfer | Never create portfolio activity or income/expense |
| Deleted activity | Exclude from holdings; retain row for audit |
| Full sell | Derived holding zero; retain asset and activity history |
| Legacy investment rows | Leave as cashflow only; no guessed asset data |

## 10. Test Strategy

### 7A.2 migration tests

- Fresh v9 database contains all new tables, constraints, and indexes.
- v8 database migrates to v9 without changing transactions, categories,
  accounts, transfers, settings, UUIDs, soft deletes, or financial totals.
- Populated upgrade includes legacy-imported and soft-deleted rows.
- Migration does not create assets or activities from historical categories.
- Older supported backup snapshot migrates before restore validation.
- Reports, account balances, Dashboard totals, and transfers reconcile before
  and after an empty asset migration.

### Domain/persistence foundation tests

- Asset UUID and stable enum strings round-trip.
- Asset type and action unknown values fail safely.
- Type plus normalized symbol uniqueness behaves as documented.
- Asset archive state does not remove activity history.
- Fractional values `0.015`, `0.000125`, `5.25`, and `123.4567` round-trip
  exactly through the fixed-point value object.
- Excess precision and integer overflow are rejected.
- Opening activity accepts null price and total amount.
- Nullable source transaction works; valid foreign key links work; restricted
  invalid links fail.
- Holdings aggregation excludes soft-deleted activities and handles zero after
  a full sell.
- Positive/negative adjustment semantics are deterministic.
- No negative-holding workflow is permitted once buy/sell repository behavior
  is added.

### Later-phase tests

Buy/sell atomic cashflow, duplicate prevention, manual/API price fallback,
batch quote privacy, offline behavior, portfolio value, Net Worth, serialized
backup/restore, and UI navigation belong to their respective later phases.

## 13. Blockers Before 7A.2

No critical blocker remains for starting 7A.2, provided the fixed-point `1e8`
quantity decision and shares-as-canonical stock decision are accepted.

Items that must remain explicit implementation constraints:

- do not use binary floating point for canonical quantities or money;
- do not reconstruct historical holdings;
- keep `source_transaction_id` nullable;
- preserve v8 data and update restore schema validation for v9;
- do not introduce a networking dependency;
- do not identify historical investment categories by display strings without a
  later stable semantic-key decision.
